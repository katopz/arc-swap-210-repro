# Results

Status: T1–T4 complete on the M3; T3 (x86_64) in progress.

All runs: `scripts/hammer.sh`, the two tests in one libtest binary,
`--test-threads=2`, debug profile, **system allocator**, rustc 1.98.1.
A MYSTERY fire is a backwards version or a torn/foreign snapshot; a MUNDANE
fire is reader starvation (none occurred in any run).

## Apple M3 Max (aarch64, macOS 26.6.2, AC power, `powermode 2`), 2026-10-03

| run | arc-swap | load | mode | iters | MYSTERY | rate |
|---|---|---|---|---|---|---|
| T2 | 1.9.1 | `./load` builds (loadavg 8 → 48) | cargo per iter | 1000 | **13** (10 backwards, 3 foreign) | 1/77 |
| C1 | 1.9.1 | none self-generated¹ (loadavg 16–30) | cargo per iter | 1000 | **4** (4 backwards) | 1/250 |
| C4 | 1.9.1 | `./load` builds (loadavg up to 55) | direct binary (`-d`) | 1000 | **10** (7 backwards, 3 foreign) | 1/100 |
| C3 | **1.9.2** (latest) | `./load` builds (loadavg up to 83)² | cargo per iter | 300 | **1** (backwards) | 1/300 |
| C2 | `genlock-load` fork (`RwLock<()>` default) | `./load` builds (loadavg up to 79)² | cargo per iter | 1000 | **0** | — |

¹ Another, unrelated process on the box was running a multi-threaded test
suite (≈8 cores) throughout, so C1 is "no build load generated by this
harness", **not** a quiet box. A Miri run overlapped C1 for about one minute
(roughly iterations 550–600).
² Miri (T4) ran concurrently with C2 and C3, which only adds load.

What the signatures say:

- **Every fire reads the OTHER instance's data.** `no_torn_read` (100 000
  versions, fill `a = v, b = 2v`) jumped back to a version ≤ 1000, which is
  `update_read`'s whole range; e.g. `2318 -> 114`, `4589 -> 985`. Or it saw
  `a == b == v`, `update_read`'s fill pattern. In the other direction,
  `update_read` (≤ 1000 versions, fill `a == b`) saw `v=1351, a=1351, b=2702`:
  a version it never reaches, in `no_torn_read`'s fill pattern.
- A random memory fault cannot produce a complete, internally consistent
  snapshot of a **different** live structure. Freed-block reuse can, and
  this is the same signature the original quarantine-allocator experiment
  linked to reuse.
- C4: re-invoking cargo every iteration is **not** required. Running the
  binary directly fires at a similar rate.
- C3: the latest release, 1.9.2 (docs-only change), reproduces.
- C2: replacing the debt/hazard fast path with `RwLock<()>` gives **0 / 1000**
  under heavier load. At C4's 1/100 rate, the chance of seeing 0 is
  ≈ 4·10⁻⁵ (≈ 2·10⁻⁶ at T2's rate).

## T4: Miri (`cargo +nightly miri test`, nightly 2026-09-29)

`miri_both_scenarios_concurrently` (both scenarios on four threads in one
test, `cfg(miri)` only, scaled to 200 / 400 updates),
`MIRIFLAGS=-Zmiri-many-seeds=0..64`: **64 / 64 seeds pass, 0 UB reported.**

Caveat printed by Miri: `integer-to-pointer cast` at
`arc-swap-1.9.1/src/debt/helping.rs:324`
(`(control & !TAG_MASK) as *mut Handover`): *"Miri might miss pointer bugs
in this program"*. Miri's provenance tracking is weakened on exactly the
helping path. The scaled iteration counts are also about 250x smaller than
the native runs.

## T3: x86_64 (Windows 11, MSVC, rustc 1.98.1)

- Cargo-per-iteration mode costs 40–60 s per iteration there under load. It
  was stopped at 50–74 iterations with 0 fires, which is uninformative
  (≈ 0.7 fires expected at the M3 rate).
- Direct mode (`-d`) under `./load` builds: in progress.
- x86 is TSO (stronger ordering than aarch64), so a fire there is strong
  evidence and a non-fire is weak.

## Reproduce

```sh
scripts/hammer.sh -n 1000 -l none    # C1
scripts/hammer.sh -n 1000 -d         # C4 / T3
git switch v1.9.2-control   && scripts/hammer.sh -n 300    # C3
git switch genlock-control  && scripts/hammer.sh -n 1000   # C2
MIRIFLAGS="-Zmiri-many-seeds=0..64" cargo +nightly miri test --lib miri_both   # T4
```
